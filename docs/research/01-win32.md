# 01. Win32 계열 자동화 현황 (A1 클래식 메뉴 / A2 MFC 공용 컨트롤 / A3 Ribbon)

조사일 2026-10-26. 태그: [fact-cited] 출처번호, [inference], [assumption], [미확인].

## A1 Win32 클래식 메뉴 (메모장, regedit)
1. 현황
 - Windows-MCP(CursorTouch): UIA 트리 + 스크린샷 + 마우스/키보드 + PowerShell. Click/Type/Shortcut/Snapshot/WaitFor 등. 스타 10.3k, MIT, 이슈 25건 [fact-cited][1]. 마지막 커밋일 [미확인].
 - pywinauto: win32 백엔드(기본) / uia 백엔드. `menu_select`로 메뉴 경로 조작. 스타 6.2k, 이슈 498건, 취미 프로젝트 [fact-cited][2].
 - FlaUI(UIA2/UIA3, 스타 3.2k) [fact-cited][3], WinAppDriver(스타 4.1k, 이슈 1.1k; MS가 수년간 미관리, 마지막 정식 릴리스 2020~2021 [fact-cited][4][5]).
 - AutoHotkey/AutoIt: `PostMessage`/`ControlClick` 관행. 1차 문서 직접 확인 못함 [미확인].
2. 없다면 왜: 해당 없음(도구 풍부). 단 "명령 ID 목록을 정적으로 문서화"하는 도구는 못 찾음 [inference].
3. 한계와 돌파
 - 기존 도구는 런타임에 메뉴를 열어보며 탐색 → 메뉴 펼침/포커스 의존, 느림(Windows-MCP 동작 간 0.2~0.5초 [fact-cited][1]).
 - 돌파: WM_COMMAND는 메뉴 선택 시 wParam 하위워드=메뉴 ID, lParam=0 [fact-cited][6]. 단 MNS_NOTIFYBYPOS 메뉴는 WM_MENUCOMMAND(인덱스)를 쓰므로 ID 전송 불가 [fact-cited][6]. 최소화 상태에서 가속키는 WM_COMMAND를 안 보냄 [fact-cited][6] → 메뉴 ID 직접 전송이 더 견고 [inference].
4. 우리 가치
 - 실행 없이 RT_MENU/RT_ACCELERATOR에서 ID·단축키·이름 일괄 추출. 로컬 실측: 메모장 `map` → 작업 38개 전부 ID 매핑(예: 새로 만들기=1, 열기=2, 저장=3) [fact-cited: 로컬 실행 결과, %TEMP%\apphelm-research\g1\notepad.ops.md].
 - 메뉴를 열지 않고 ID 직송 → 동적 메뉴(동적 생성 항목)는 못 얻음이 한계 [inference].

## A2 MFC 공용 컨트롤 (SysListView32/SysTreeView32)
1. 현황
 - pywinauto win32 백엔드가 ListView/TreeView 래퍼 제공(README엔 컨트롤 목록 없음 [fact-cited][2], 래퍼 세부 [미확인]).
 - NVDA는 SysListView32 전용 NVDAObject 보유(소스 사본만 확인) [fact-cited][7][미확인: 원본 저장소 미열람].
 - UIA 계열(FlaUI, Windows-MCP)은 공용 컨트롤을 UIA 프록시로 읽음 [inference].
2. 없다면 왜: 도구는 존재. 다만 "정적 문서화"는 부재.
3. 한계와 돌파
 - LVM_GETITEMTEXT의 LVITEM 포인터는 호출자 주소공간 → 타 프로세스에 직접 SendMessage하면 멈춤/오작동 보고 있음 [fact-cited][8 (포럼 사례)]. LVS_OWNERDATA 스타일은 미지원 [fact-cited][8].
 - 돌파(범위 내): 라이브러리 래퍼(pywinauto) 또는 UIA 백엔드 사용 [inference]. 프로세스 메모리 읽기·주입 방식은 범위 밖이라 쓰지 않음.
 - 오너데이터/커스텀 드로우 목록은 텍스트 추출 불가 → 스크린샷/OCR 폴백 [inference].
4. 우리 가치
 - MFC 여부는 PE 임포트(mfc*.dll)로 정적 판별, 메뉴/대화상자/문자열 테이블은 리소스에서 A1과 동일 경로로 확보 [inference, 미실측].
 - 컨트롤 내용(행 데이터)은 런타임 영역 → UIA/LVM 라이브 조작과 결합해야 함.

## A3 Windows Ribbon (그림판, 탐색기)
1. 현황
 - 프레임워크: 마크업(XAML 유사)을 UICC로 바이너리 리소스 컴파일, Command ID로 C++ COM 핸들러에 바인딩 [fact-cited][9]. 접근성 표준 준수 명시, UIA 세부 서술은 없음 [fact-cited][9].
 - 자동화: UIA 기반 도구(Windows-MCP, FlaUI, pywinauto uia)가 사실상 유일 경로 [inference]. 네이티브 Ribbon 전용 도구·실측은 못 찾음 [미확인].
 - 서드파티 리본(DevExpress/Infragistics)은 탭 전환 시 UIA 요소 누락/이미지로 노출된 사례 [fact-cited][10] — 네이티브 Ribbon과 동일하다는 보장 없음.
2. 없다면 왜: 전용 도구 부재 = 수요 적음 + 기술 장벽(정적 리소스가 바이너리 UI 포맷, 명령은 COM) [inference].
3. 한계와 돌파
 - 정적 추출이 약함(AppHelm PARTIAL과 일치). 탭 전환 후에만 컨트롤이 나타나는 지연 노출 [inference].
 - 돌파: 탭별로 선택 후 UIA 재스냅샷, 이름·AutomationId 캐시. 단축키(Alt 키팁) 경로 병용 [inference, 미실측].
4. 우리 가치
 - Ribbon 리소스(UIFILE)에서 Command ID/문자열 일부를 정적으로 얻을 수 있으면 UIA 탐색 비용 절감 [assumption, 검증 필요].
 - 현실적 가치는 "정적 힌트 + 런타임 UIA 보정"의 하이브리드.
